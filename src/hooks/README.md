# KSA Metal Hooks

The hooks are the part of KSA Metal that changes the game's C# code, in memory, when the game starts, with
[Harmony](https://github.com/pardeike/Harmony). `KSA.dll` stays as it is on disk, and the repository holds only the
hooks' own code. Most of them are patches that make drawing cheaper; the others add the port's part of the game: the
Mac Port tab in the game's settings, a Restart button that works in the app, and the benchmark's runs.

The main README says what the hooks are, in short ([The hooks](../../README.md#the-hooks)). This file has the
detail: how they load, the rule every hook follows, what each one changes, the settings they read, and how to build
and test a change.

| Path | What it holds |
|---|---|
| `Hooks.cs` | the list of hooks in the order they apply, and the rule they follow: `Skip`, `Find`, `Fail` |
| `Settings.cs` | the settings as the hooks read them, a typed property each, with `Settings.Generated.cs`, which the build makes from the settings table ([Settings](#settings)) |
| [`patches/`](patches/) | the patches to the game's rendering and physics ([The patches](#the-patches)) |
| [`app/`](app/) | the port's part of the game: Restart, the documents folder, windows and UI coordinates, displays, HDR, mods' generic patches, frame captures, the benchmark's runs ([The port's part of the game](#the-ports-part-of-the-game)) |
| [`tab/`](tab/) | the Mac Port tab and its presets |
| [`loader/`](loader/) | the startup hook, which applies the settings and loads the hooks ([How they load](#how-they-load)) |

Each folder of the hooks' assembly is a namespace of its own: `KsaMetalHooks.Patches`, `KsaMetalHooks.App`,
`KsaMetalHooks.Tab`; `Hooks.cs` and `Settings.cs` are `KsaMetalHooks`, the root, where the loader finds
`KsaMetalHooks.Hooks`. The settings table, `port-settings.toml` and the environment are read by the port settings in
the port's shared library ([`../shared/settings/`](../shared/settings/)), which the loader and the hooks share.

## How they load

The launcher names `KsaMetalHooksLoader.dll` in `DOTNET_STARTUP_HOOKS`, so .NET runs it before the program it starts:
KSA itself, or StarMap, which loads KSA into a load context of its own. The loader
([`loader/Loader.cs`](loader/Loader.cs)) references nothing of the game. First it applies the port settings
([Settings](#settings)). Then it waits until `KSA.dll` is loaded, loads `KsaMetalHooks.dll` into the same load context
and applies it; with the `hooks` setting off it stops after the settings, except for a benchmark run. It loads no
Harmony itself: under StarMap, the hooks use the copy StarMap has already loaded; without StarMap, they find the app's
copy next to them, in `Contents/Resources/Hooks/`, with the port's shared library. The benchmark's director, which the
hooks give every frame, is in `Contents/Resources/Benchmark/`.

## The rule every hook follows

A hook is a class whose `Apply` `Hooks.cs` runs, and it goes by the class's name, in the log and in the settings
table. It finds its targets by name and the code it changes by pattern: an instruction it expects exactly once, or the
call that follows a field it knows. It looks everything up before it changes any of the game's state. When
something isn't where it expects it, typically after a KSA update, the hook throws `Skip`. Everything that hook had
changed is undone, and `console.log` says so:

```text
[hooks] TerrainCache: on
[hooks] OutlineSkip: on
[hooks] OverlaySkip: on
[hooks] OceanBlending: on
[hooks] CloudShadows: off
[hooks] ShadowSearch: off
[hooks] CrewPortraits: on, when shown
[hooks] WorkerPark: on, 0.25 ms
[hooks] LoadingPace: on
[hooks] RenderScale: skipped, the game's code changed (the sun's radius not found)
[hooks] HiddenPartsSkip: on
[hooks] Documents: off
[hooks] Restart: on
[hooks] Hdr: on
[hooks] Presets: on, Apple M5, 16 GB
[hooks] MacPortTab: on
[hooks] BenchmarkRun: ready
```

A hook that throws anything else has a bug of its own: it is undone the same way, and `console.log` says `failed`,
followed by the error and where it happened. While the game runs, the code the game calls of the terrain cache, the
ocean blending, the overlay skip, the crew portraits, the HUD layout and the Mac Port tab catches its own errors the same way: the hook says `failed while
the game ran`, once, and hands the game its own behaviour from then on. The render scale changes the whole frame and
can't hand it back halfway: an error there reaches the game. The game then runs as it would without that hook; the Mac Port tab
shows the settings it does as unavailable, and a benchmark run fails, so a release can't pass its test with a hook
skipped or failed. The patches change what is drawn and how much work drawing it takes; only the tumbling physics and
the debris settling, off by default, change what the game simulates: a piece that settled stays settled in a save, and one sunk inside a planet is gone.

## The patches

| Hook | Tab row | File | How |
|---|---|---|---|
| `TerrainCache` | Terrain Cache | [`TerrainCache.cs`](patches/TerrainCache.cs) | a prefix on `PlanetRenderer.GenerateMeshData` compares the inputs of the terrain's height passes (body, mesh level of detail, snapped texture rotation, height buffer) with those the frame slot's buffer was last computed for; a transpiler routes the two dispatches of those passes through a check that skips them when nothing changed. They run every 2 s anyway, for the streamed heightmap. The normals pass is skipped too while the mesh's rotation has turned less than 1e-4 rad (its normals don't depend on where the camera is) |
| `OutlineSkip` | Skip Unused Outlines | [`OutlineSkip.cs`](patches/OutlineSkip.cs) | `Part.Selected`'s setter counts the selected parts; `PartSelectedRenderer.Run` returns early while there are none (only selected parts mark the image it outlines) |
| `OverlaySkip` | Skip Unused Overlays | [`OverlaySkip.cs`](patches/OverlaySkip.cs) | every frame, after the bloom, `GizmoPass.Run` clears an image of its own and blends it over the whole view, twice, also without gizmos; with MSAA, `SingleToMultisamplePass` first copies the main view into its multisampled image for the orbit lines and gizmos, and `ResolveAttachments` resolves it back after them. A prefix returns from `GizmoPass.Run` while no gizmo has instances; in the main view without orbit lines either, a prefix skips the copy, and the resolve after it runs with the target's colour hidden, so it resolves depth only (the copy gave every sample the view's own value). Other views keep both: they draw their translucent meshes in between. Same image; with MSAA x2 about 0.2-0.5 ms less GPU time a frame on an M5 |
| `HiddenPartsSkip` | Skip Hidden Vessel Parts | [`HiddenPartsSkip.cs`](patches/HiddenPartsSkip.cs) | the vessels' shaders mark selected parts in the selection outline's mask, a store from the fragment shader, so they run before the depth test and shade every hidden fragment too. Same image; on an M5 at the game's own settings the cockpit about 11 % less GPU time a frame |
| `OceanBlending` | Skip Unused Ocean Blending | [`OceanBlending.cs`](patches/OceanBlending.cs) | the ocean blends into the image behind it with its alpha, which its shader writes as 0 unless the shore filter fades the ocean out, above 10 km only. Same image; at sea level with MSAA about 10 % less GPU time on an M5 (no read of what is behind, hidden-surface removal for the overlapping waves). It checks the shader lines it rests on and skips when they changed |
| `FadedSmoke` | Clear Faded Smoke | [`FadedSmoke.cs`](patches/FadedSmoke.cs) | a plume that merges into a group's ends at `MemberEndAgeSeconds`, from `GetEntrainedRadiusAge`, which grows with the cube of the boosters' spacing up to the plume's expanded radius (13,500 to 312,000 s measured), while its density reaches zero at its lifetime (420 s for solid motors, 20 s for liquid engines). `PlumeSegmentMaintenance.ApplySegmentsAge` now removes a segment at the shorter of the two, so warp can't stretch and split invisible segments up to the 65,536 limit and the smoke's shadow cascades don't draw them. A rocket with 16 solid motors, warped until everything has landed: 1.3 -> 20-43 fps in the worst stretch, 5 -> 36-47 fps afterwards, at the defaults. Removing about 65,500 segments from a paused daylight view moves no pixel by more than 7 of 255, and those only over the moving sea; with a live plume in view, 0.44 % of pixels move by more than 2 of 255, against 0.21 % between two shots with nothing removed |
| `ShadowSearch` | Simpler PCSS Shadows | [`ShadowSearch.cs`](patches/ShadowSearch.cs) | with `simpler_pcss_shadows` on and the game's soft shadows (PCSS), each pixel searches the shadow cascades for blockers as far as the widest penumbra the sun casts, 1 m: hundreds of texels in the cascades near the camera, 16 taps that miss the GPU's caches. A prefix on `CascadedShadowMap.UploadCascades` puts a limit of 32 texels in the cascades' spare `_pad1`, which the porter's shader edit ([`../porter/shader-edits/`](../porter/shader-edits/)) reads (0: the game's search). On an M5 at the Quality preset, with the edit that skips shadows where there is no sunlight already in, it takes about 8 % off the GPU time of grass (fur 32.4 -> 29.7 ms) and 3 % off views with shadows near the camera; the cockpit doesn't change. A penumbra is about 1/200 of its caster's height, so in the three nearest cascades a shadow cast from more than about 8, 30 or 85 m above can get a sharper edge; none of the views tried showed a change |
| `MilkyWayBake` | Baked Milky Way | [`MilkyWayBake.cs`](patches/MilkyWayBake.cs) | with `baked_milky_way` on: `MilkyWay.frag` works out the Milky Way's dust clouds for every pixel of its band from the view direction alone, about 90 lookups of a noise texture each, 1-2 ms of a frame with much sky on an M5 (5-7 at the game's Milky Way Quality Ultra). The porter's shader edit ([`../porter/shader-edits/`](../porter/shader-edits/)) moves the clouds into a function and writes `MilkyWayBake.comp` from the same file. A postfix on `MilkyWayRenderer.GenerateNoise` fills an 8192 x 512 strip of the clouds over the band (8 MB) and puts it in the noise's place, so the game binds it to the shader, which reads the clouds from it when its texture isn't square; a postfix on `BuildPipeline` fills it again when the quality (the clouds' octaves) changes. At the default field of view (50°) on a Retina display a texel of the strip is about 1.7 pixels, and the sky's pixels change by at most 1 of 255 in the views tried; the clouds are sampled from the strip, so zoomed in or in a larger window their finest grain can look softer. With the strip, at the Performance and Balanced presets, Milky Way Quality High costs what Low and Medium do (every view within 0.1 ms; Ultra not measured) |
| `TumblingPhysics` | Lighter Tumbling Physics | [`TumblingPhysics.cs`](patches/TumblingPhysics.cs) | with `lighter_tumbling_physics` on: `PhysicsStates.ComputeTimestep`'s spin limit, (pi/6)^2 / w^2, gets its square root in free flight, at most 1/60 s and never shorter than the game's (a vehicle with ground or water contact keeps the game's step: its g-load decides whether it breaks, and depends on the step), so from about 4 rad/s on a tumble takes steps of up to 30 degrees and not ever shorter ones down to the 1 ms minimum (the square root alone lets falling pieces pass through the ground), and `KinematicStates.ClampVelocities`' spin cap goes from 5236 to 200 rad/s. These two and `KinematicStates.UpdateFromBepu` are inlined, so their callers call changed copies (reverse patches). With four rockets launched in turn at x32, physics substeps fall from 85,000-310,000 to 36,000-39,000 and the worst vehicle job from up to 324 ms to 71-76 ms. A rocket spun at 3, 8 or 30 rad/s falls and breaks up on landing as without it, with no piece through the ground in 24 landings; at 1000 rad/s it loses the spin above the cap at once |
| `CloudShadows` | Fewer Cloud Shadow Updates | [`CloudShadows.cs`](patches/CloudShadows.cs) | with `fewer_cloud_shadow_updates` on: the slices `CloudShadowVolume.UpdateVolumeDensity` refreshes per frame, 24 and 8, become 6 and 2 |
| `DebrisSettle` | Debris Settles in Warp | [`DebrisSettle.cs`](patches/DebrisSettle.cs) | with `debris_settles_in_warp` on, for a piece (what `PartFailure.IsExpendable` means: nobody flies it, no crew is on it, which also covers spent stages and the parts of a breakup the game doesn't mark as debris; with no engine firing). A postfix on `UpdateSimFromVehicle` gives a piece a sleep energy of 0.5, not 0.005, after 32 steps; one on `UpdateVehicleFromSim` and `ReadBackFromSim` makes a piece asleep and that slow Landed if its contacts reach the ground, and from x64 one touching the ground in this step, 6 game seconds after its first touch (at the first touch whole rockets stay standing), Landed and asleep, unless a camera follows it or a vehicle somebody flies touches it; a prefix on `DetectStructuralFailure` keeps that stop from reading as an impact. **Settled pieces:** a prefix on `VehicleUpdateState.SetCurrentOrbit` turns off the terrain search for a Landed piece and a postfix marks its one-orbit plan complete. **Pairs in a bubble:** `ComputeBubbleUnconstrainedTime` holds a bubble to 1/60 s for any pair side by side, even in a frame's step of an hour; a prefix returns no limit for pieces on rails and Landed vehicles, and from x1024 for any vehicles on rails. **Pairs of bubbles:** a prefix on `VehicleUpdateTask.HasValidClearance` answers yes for two bubbles of pieces, for a piece and anything more than 5 km away, and from 2 s steps for anything more than 50 km away, without the width of a wide bubble beyond 5 km: the game's check, with long steps, merged every crossing of orbits, the wider bubble reaching more, until one frame had hundreds of vehicles over 800 km in one bubble (stalls of 25-50 s). **Sunk pieces:** a postfix on `Universe.ApplyVehicleSolvers` destroys a piece more than 100 m below the body's lowest terrain: one past the ground at speed sails on inside the planet at the spin cap, in 1 ms steps, the game hanging for as long as it lasts. Saved and loaded, a settled crash stays where it lay. |

## The port's part of the game

| Hook | File | How |
|---|---|---|
| `Presets` | [`Presets.cs`](tab/Presets.cs) | the tab's Performance, Balanced and Quality, and Game Defaults with the same settings at their defaults (a new `GameSettings`, as the game's Reset makes; the table's defaults): each gives every game setting any of them sets (fields of `GameSettings` and `GameSettings.Graphics`, found by name when the game starts, each value checked against its type) and its port settings, the settings table's presets column. The Mac's memory (`hw.memsize`; 8 GB or less: shadow maps and textures at most 2048) and chip (`machdep.cpu.brand_string`; M1 and M2: no `IVARayTracing`) decide some of them (not Game Defaults', the same on every Mac). In Fullscreen each also sets the Resolution to the size of the screen's desktop ([`Displays.cs`](app/Displays.cs): the GLFW shim's answer, the display's current mode or, while the game's Fullscreen has it switched, the one it had before), so the render scale alone sizes the 3D view and the display keeps its mode; Windowed and Borderless keep theirs. A preset's button sets them on the game's pending copy of its settings and as the tab's pending values, so the game's pending marks, Apply, Discard and restart popup handle them as any change |
| `MacPortTab` | [`MacPortTab.cs`](tab/MacPortTab.cs), [`MacPortWidgets.cs`](tab/MacPortWidgets.cs) | the settings window's rail gets a tab first, in a group of its own (its arrays are read-only fields, so the methods that read them read longer copies, and `OnDrawUi`'s `NavRail` call draws two groups), whose rows are drawn with the game's own widgets once the content's body has begun. The rows come from the table of the port settings (`Contents/Resources/port-settings.txt`), their values from `port-settings.toml`, and what the game runs with from the environment the loader set. The tab's pending values go with the game's pending copy of its settings, so the game's pending marks, Apply, Discard, Reset and Close, and its "restart required on apply" popup, all count them. Apply writes the changed lines into the file; live settings take effect at once. Under Render Scale a line gives the 3D view's size in pixels with the upscaling and render scale shown, worked out as [`RenderScale.cs`](patches/RenderScale.cs) does |
| `Restart` | [`Restart.cs`](app/Restart.cs) | the popup's Restart starts the game's own executable again, which in the app is .NET's `dotnet` with no program: the game only quits. A transpiler replaces that call: it starts the app again through macOS (`open -n`, which hands the app its own environment: the game's, without what the port settings set, and `KSA_PORT_WAIT`, the game's process id), and the new launcher waits until this game has quit. A process the game started itself would not survive: when the app was started from the Finder, macOS ends what a quitting app leaves running. The new game reads the port settings as any start does |
| `Hdr` | [`Hdr.cs`](app/Hdr.cs) | the driver shows the game's HDR output with its HDR Paper White (Display) at the display's SDR white and tells macOS its HDR Peak Brightness ([Presentation](../ksa-metal/README.md#from-vulkan-to-metal)); the game keeps paper white to itself and sends the peak only when it rebuilds the swapchain: a postfix on `GameSettings.ApplyTo(GlfwWindow)`, where the game hands its Display settings to its renderer when it starts and at every Apply, passes `HdrOutput.PaperWhiteNits` and `PeakNits` to the driver (`ksaMtlHdrNits`). Without it, the driver takes the game's defaults, 200 and 1000 nits, and the peak the swapchain was built with |
| `GenericDetours` | [`GenericDetours.cs`](app/GenericDetours.cs) | mods' Harmony patches on generic methods over reference types: on arm64, MonoMod stops at the method's instantiating stub, so the arguments arrive shifted by one or the patch never runs, and it crashes the game when a mod reads them. The first hook, so before any mod patches: each detour starts from the shared method, read from the stub's jump. It changes nothing in the game. It also keeps these patches running after tiered compilation, which x64 doesn't. As on x64, a patch on `M<string>` also runs for `M<object>`, and of patches on both only the last one runs. Limits: with arguments on the stack, direct calls skip the patch (the log says so); a shared method returning a struct through a return buffer, or a virtual method of a generic struct over a reference type, can't be patched (MonoMod's errors, with or without this); constructors aren't covered; a mod with its own copy of Harmony isn't covered; with the hooks off, it isn't applied |
| `UiViewSize` | [`UiCoordinates.cs`](app/UiCoordinates.cs) | the main view's size is the render size, smaller than the window below a render scale of 1, while what's drawn on it is in the window's points: a panel placed from it landed short of the screen's edge, and a mod's overlay sized from it clipped what it drew. While the frame's UI is drawn, and in mods' code at the frame's end, the size is the window's, for the game and mods alike; the render passes keep the render size. Code running at other times, such as a mod's patch on the views' update, sees the render size |
| `WindowOrigin` | [`UiCoordinates.cs`](app/UiCoordinates.cs) | ImGui's coordinates start at the desktop's corner, and a mod that takes them to start at the window's is right only with the window there: windowed, or on a display left of the main one, its overlay became an OS window of its own and what it drew was off by the window's position. The desktop now starts at the window's corner, for everything the game and mods read of windows and displays. Placing the main window itself keeps the real positions; a mod that moves it sets real positions but can only read relative ones (no listed mod does) |
| `ExtraWindows` | [`ExtraWindows.cs`](app/ExtraWindows.cs) | the game's extra windows (detached gauges, pop-outs) are created at macOS's floating level, and GLFW puts a fullscreen window above that, so a window detached in Fullscreen mode went behind the game. While the main window is at the floating level or above (Always on Top, Fullscreen), the extra ones are one above it |
| `Documents` | [`Documents.cs`](app/Documents.cs) | `STARMAP_INSTANCE_PATH` moves the game's documents folder, as StarMap does, also without StarMap (the benchmark's runs) |
| `FrameCaptureCommand` | [`FrameCaptureCommand.cs`](app/FrameCaptureCommand.cs) | a postfix on `Program.OnFrame` adds the console command `framecapture [note]`, for a picture that goes wrong now and then: in `framecaptures/<date>_<time>` in the documents folder, KSA Metal's image of that frame, the next frame's passes (`passes/`: the images after each draw and of the frame's end, with their numbers in `passes.txt`), an Xcode frame capture of a frame after them (with `frame_capture = true` and 20 GB free) and KSA Metal's image of the frame after it, the camera's place, the warp and the driver's numbers, the log and the settings. After a GPU failure it saves no passes or capture, since the GPU refuses the game's work. The capture stalls the game while it is written |
| `BenchmarkRun` | [`BenchmarkRun.cs`](app/BenchmarkRun.cs) | a postfix on `Program.OnFrame` gives the benchmark's runs every frame ([`../benchmark/director/Runs.cs`](../benchmark/director/Runs.cs)), with the hooks' log, the summary of what they applied and the game's restart: a run starts from the game's first frame when the game starts with `KSA_BENCH_OUT` naming a run's folder, whose `run.json` holds the run's options (`RunOptions`, written by the benchmark's report program), or from the Mac Port tab. A run in the game that is open saves it (to disk and in memory), sets the world to a new game's through the game's own loading (`Universe.DeserializeSave`), and loads the saved game again at the end; the benchmark then writes the report with the report program |

## Settings

The hooks, KSA Metal and its shims read environment variables, which the loader sets from `port-settings.toml` when
the game starts ([`loader/PortEnvironment.cs`](loader/PortEnvironment.cs), with the port settings in the shared
library, [`../shared/settings/`](../shared/settings/)): a setting's variable is `KSA_MTL_` and its key in capitals,
with 0 for off and 1 for on. One set before the game starts wins over the file, and the Mac Port tab shows its row as
set outside. The loader sets each variable twice, for .NET, which keeps its own copy of the environment, and with
`setenv` for KSA Metal and the shims, which read theirs when the game first uses them. It also sends the game's output
to `console.log` and copies the file's template for a new player. The hooks read their settings through the library,
each as a typed property of [`Settings`](Settings.cs) named after its key (`terrain_cache`: `Settings.TerrainCache`):
a variable that is unset, holds none of the setting's values (`console.log` says which), or belongs to a setting whose
needs aren't met means the default. The table
[`../shared/settings/port-settings.txt`](../shared/settings/port-settings.txt) says which hook does each setting;
those of the hooks:

| Setting | Effect |
|---|---|
| `upscaling` | `off`, `metalfx` or `spatial` |
| `render_scale` | 0.5 to 2: a fraction of the window's size in points (it needs `upscaling`) |
| `frame_interpolation` | on: frame interpolation (KSA Metal reads it too) |
| `skip_game_anti_aliasing` | off: with MetalFX, the game's anti-aliasing setting applies (but CMAA2) |
| `fewer_cloud_shadow_updates`, `lighter_warp_cloud_shadows`, `lighter_plume_shadows`, `simpler_pcss_shadows`, `baked_milky_way`, `crew_portraits_at_15_fps`, `lighter_tumbling_physics`, `debris_settles_in_warp` | on: the Extra Performance rows |
| `skip_hidden_crew_portraits`, `fit_hud_to_display` | off: the game's own crew portraits and flight HUD; both change while the game runs |
| `terrain_cache`, `skip_unused_outlines`, `skip_unused_overlays`, `skip_hidden_vessel_parts`, `skip_unused_ocean_blending`, `idle_thread_sleep`, `loading_screen_fps_cap`, `clear_faded_smoke` | off: leave out that patch |
| `worker_park_ms` | milliseconds: how long an idle job worker spins before it sleeps (0.25) |
| `trail_caches` | `<large>,<small>,<tiny>[,<segments>]`: the smoke's volume cache budgets in MiB (Experiments; unset: the game's) |
| `trail_shadows` | `<cascades>,<resolution>,<metres>`: the smoke's sun shadow cascades (Experiments; wins over `lighter_plume_shadows`; unset: the game's) |
| `harmony_generic_detours` | off: without generic detours, to tell whether a mod's problem comes from them (Troubleshooting) |
| `hooks` | off: the game starts without the hooks, but for a benchmark run, which they start |

To find out which patch causes a problem, turn it off in the Mac Port tab (Optimizations), or set it in the file.

## Build and test

`./build.sh` builds both assemblies against the KSA it is given, with the shared library and the benchmark
([`scripts/build-dotnet.sh`](../../scripts/build-dotnet.sh)): `KSA.dll` and the benchmark's director are references
only. Harmony comes from the `Lib.Harmony` package on nuget.org, pinned in
[`cmake/dependencies.cmake`](../../cmake/dependencies.cmake).

Before it, the port settings' generator checks the table against the hooks
([`../shared/settings/`](../shared/settings/)): the hooks it names exist, and the hooks read the settings it says they
do and no others; it stops the build when they don't.

For the patches, the benchmark is the test. `--port` changes a port setting for one run, and the report lists the port settings and
what the hooks did:

```bash
./benchmark.sh --fast --port hooks=false                  # without the patches
./benchmark.sh --fast --compare <that run>                 # with them: faster, the same screenshots
./benchmark.sh --fast --port terrain_cache=false           # without one of them
./benchmark.sh --fast --port upscaling=metalfx --port render_scale=0.5 --set antialiasing=None
```

To see the game's code a patch works on, Harmony's `PatchProcessor.GetOriginalInstructions` lists a method's IL.
